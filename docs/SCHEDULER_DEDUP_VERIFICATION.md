# スケジューラ二重実行防止の検証（7時台含む）

7時台のみ二重実行が発生する事象への対策と、**各スロットで「必ず1回は動く」**ことをなるべく保証するための設計です。

---

## 1. 変更概要

| 変更 | 目的 | スキップ条件 |
|------|------|----------------|
| 早期 return 時のロック解放 | ロック・フラグのリーク防止 | 当日実行済み（同一プロセス） / マネージャー未初期化 |
| execution_id にミリ秒・PID付与 | 同一秒の複数実行の識別、二重実行時のプロセス判別 | なし（常に実行） |
| **完了時のみスロット記録** | 二重防止しつつ「1回は完了」を優先 | 同一スロットが 25 分以内に**完了済み**の場合のみスキップ |
| ドキュメント（外部 cron 注意） | 二重トリガー防止の注意喚起 | なし |

**スロットの意味**: スケジュールは **1:00・7:00・13:00・19:00（JST）の4回**。それぞれ 1am / 7am / 1pm / 7pm の「スロット」に対応し、**各スロットは1日に1回しかトリガーされない**（例: 7時台スロットは 7:00 の1回だけ。13:00 は別スロットなので、7時台の「次」のトリガーではない）。「このスロットは**完了した**」を DB に記録するのは **成功完了時だけ**。開始時に「主張」はしない。

- **開始時**: `has_slot_completed_recently(slot_key, 25)` で「25分以内に完了済み」ならスキップ。
- **成功完了時**: `mark_slot_completed(slot_key)` で記録。

→ 1本がクラッシュしても記録されないので、別プロセス（または後続トリガー）が同じスロットで再実行でき、**「各スロットで必ず1回は完了する」**可能性が高くなる。

---

## 2. 「必ず1回動く」の保証

### 保証できるケース

| ケース | 結果 |
|--------|------|
| 通常（1プロセス・1回発火） | その1回が実行され、完了時にスロット記録。**1回完了**。 |
| 2プロセス同時（7:00 に A と B） | A がロック取得して実行。B はロックで待機。A が**完了**すれば `mark_slot_completed` され、B はロック取得後に「完了済み」でスキップ。**1回完了**。 |
| 2プロセスで先に動いた方がクラッシュ | A がロック取得して実行、クラッシュ（記録なし）。B がロック取得 → 「完了済み」なし → B が実行して完了・記録。**1回完了**。 |

### 保証できないケース

| ケース | 結果 |
|--------|------|
| **単一プロセスで、その1本がクラッシュ** | 誰も `mark_slot_completed` しない。ただし**各スロット（1時・7時・13時・19時）は1日1回ずつしかトリガーされない**ので、例えば「7時の1本だけ」がクラッシュした場合、同じ「7時台スロット」を再度トリガーするのは翌日の7時までない（13時・19時は別スロットのため、7時台の自動リトライにはならない）。**手動で `POST /api/scheduler/execute`（force=True）** すればその時点で再実行可能。 |

→ **複数プロセス・複数回トリガーがある場合**（7時台に2本走る事象など）は、**「各スロットで必ず1回は完了する」**ように設計している。  
→ **1プロセスだけかつ、そのスロットのたった1回の実行がクラッシュ**した場合は、そのスロットは同じ日には自動では再トリガーされない（スケジュールは 1/7/13/19 時のみのため）。

---

## 3. 7:00 が「1回も動かない」パスがないことの確認

### 3.1 正常時（単一プロセス・1回だけ発火）

1. ロック取得 → 成功
2. `has_slot_completed_recently("7am_...")` → 初回は **False** → スキップしない
3. 当日実行済みチェック（メモリ） → 初回はスキップされない
4. `refresh_all_trends` 実行 → 成功完了 → `mark_slot_completed("7am_...")`

→ **1回目の 7:00 は必ず実行され、完了で記録される。**

### 3.2 二重実行防止時（2プロセス目が来た場合）

- プロセス A: ロック取得 → 実行 → **完了** → `mark_slot_completed`
- プロセス B: ロック取得後、`has_slot_completed_recently` → **True**（A が記録済み）→ スキップ

→ **1本だけが実行され、その1本は必ず「完了」まで行う。**

### 3.3 DB 障害時（has_slot_completed_recently が例外）

- `has_slot_completed_recently` の `except` で **False を返す**（fail-open）
- 「完了済みでない」とみなして **実行を許可**

→ **スケジュールは止まらない。**

### 3.4 手動実行（force=True）

- `if not force and slot_key and ...` のため、スロットチェックを**行わない**
- **常に実行可能**

---

## 4. スキップが発生する条件

| 条件 | 結果 | 「1回も動かない」か |
|------|------|----------------------|
| `_fetching_in_progress` が True | 同一プロセス内の重複のみスキップ | 1回目は動く |
| ロック取得失敗 | 他プロセスが実行中 | 他プロセスが動いている |
| `has_slot_completed_recently` が True | 同一スロットが 25 分以内に**完了済み** | その「完了」が既に 1 回 |
| 当日実行済み（メモリ） | 同一プロセスで同じ帯で既に実行済み | 前の実行が 1 回 |
| マネージャー未初期化 | アプリ異常系 | スケジューラ以外も制限 |

→ **いずれも「そのスロットが 1 回も動かない」にはならない。**

---

## 5. 結論

- **1am / 7am / 1pm / 7pm の各スロット**で、**「最大1回」**の実行に抑えつつ、**「少なくとも1回は完了する」**ようにしている（完了時のみスロット記録）。
- **2本走るような環境**（7時台に2回トリガーされる場合など）では、1本がクラッシュしてももう1本が完了すれば、そのスロットは **必ず1回は完了**する。
- **1プロセスだけで、そのスロットの1本がクラッシュ**した場合、そのスロット（1時・7時・13時・19時のいずれか）は**その日は同じ時刻に再度トリガーされない**（スケジュールが 1/7/13/19 時の4回だけだから）。必要なら手動で `POST /api/scheduler/execute`（force=True）で再実行できる。
- DB 不調時は fail-open で、スケジュールが止まらない設計である。

---

## 6. テスト・運用時の注意

- **tests/test_scheduler_email.py**: 実行時刻が 0–2 / 6–8 / 12–14 / 18–20 のときは `has_slot_completed_recently` が使われる。初回は False で実行され、完了時に `mark_slot_completed` される。短時間に同一スロットで2回呼ぶと2回目は「完了済み」でスキップされる。
- **手動リトライ**: 任意のタイミングで `POST /api/scheduler/execute`（force=True）で再実行可能（スロットチェック対象外）。
